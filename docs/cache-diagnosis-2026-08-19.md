# claude-hub 上游提示缓存失效诊断

诊断日期:2026-08-19。数据源 `~/.cc-switch/logs/claude-hub-usage.jsonl`(direct + claude-opus-5,1991 条)
与运行中 hub 的 stdout 日志 `$TMPDIR/claude1-bridge-*/hub.log`(1070 条提升事件,带 path 与计数)。
本次只做诊断,未改动任何代码或配置。

## 结论一句话

真凶就是 system 提升,但机制不是"提升结果不稳定"——提升本身完全幂等;
病根在于**被提升的 system 块数随会话轮次严格递增(实测 x47→x52,每轮 +1),
而 hub 把它们追加到顶层 `system` 末尾,顶层 `system` 位于上游缓存前缀的最前端,
于是整个前缀每一轮都在变长,messages 上的所有 cache_control 断点每轮全部失效。**

## 证据

### 1. 提升实现与落点(代码)

- 产生位置:`claude1_protocol.py:2560`,在 `_normalize_native_system_roles`(`:2516`)内。
- 落点是决定性的两行(`:2566-2568`):
  ```python
  existing = _canonical_system_blocks(result.get("system"))
  result["system"] = [*existing, *promoted]
  result["messages"] = retained
  ```
  被抽走的 system 块**追加在顶层 `system` 数组末尾**,原消息位置只留下空洞。
- 触发无条件:`prepare_request`(`:2600-2608`)对 `api_format == "anthropic"` 一律调用该函数,
  不判断上游是否原生接受 Claude Code 的 system-role 扩展。
- native 路径**不经过** `_parse_request_ir`,所以 hub 对 native 请求做的唯一改动就是这次提升。
  这与"从未出现 `HUB_DEGRADE_CACHE_CONTROL_DROPPED`"完全一致。
- Hub 侧调用点:`claude-hub.py:3335`,warning 落日志在 `:3344-3348`。

### 2. 提升是幂等的,用户的原始怀疑三条全部证伪

直接 import 现网代码跑探针(构造顶层 system 带断点 + messages 中段 system-role 带断点):

| 检查项 | 结果 |
| --- | --- |
| 同输入是否逐字相同 | `identical: True`,幂等 |
| 拼接顺序是否确定 | 确定:原顶层在前,提升块按 `messages` 索引升序追加 |
| 断点数量是否守恒 | 输入 3 个 `cache_control`,输出 3 个,不丢不增 |
| 断点是否仍指向同一段文本 | 是。`_canonical_system_blocks`(`:2108`)用 `copy.deepcopy(block)` 整块搬运,`cache_control` 与它所在的 text 一起移动,内容边界没变 |

所以"顺序不定""拼接改写导致断点指向不同文本"这两条不成立。**但方向猜对了**:
危害不在单次请求内部,而在**跨请求的前缀漂移**。

### 3. 实况:提升块数每轮 +1(决定性)

同一会话连续 6 个请求,`hub.log`(2026-08-19 11:35–11:40):

```
x47 (first: $.messages[1].role)
x48 (first: $.messages[1].role)
x49 (first: $.messages[1].role)
x50 (first: $.messages[1].role)
x51 (first: $.messages[1].role)
x52 (first: $.messages[1].role)
```

`first` 恒为 `messages[1]`,计数严格单调 +1。全量日志里这个计数从 x1 一路涨到 x85。
含义:客户端每轮新增一条 system-role 消息(位置在消息序列末尾,那里本就在最后一个断点之后,
**不污染前缀**),而 hub 每轮都把它们全部抽出、重新拼到顶层 `system` 尾部。
上游缓存前缀的拼装顺序是 `tools → system → messages`,
**动态增量因此被从"前缀之后"搬到了"前缀之前"。**

### 4. 后果签名与代码预测完全吻合

08-19 同一会话内的连续记录:

```
in=23686 cr=0     cw=46115    ← 整个 46K 前缀重写
in=25556 cr=0     cw=46136    ← 再重写,且比上次长了 21
in=27107 cr=45613 cw=544      ← 偶尔命中(该轮没新增 system 块)
in=29986 cr=0     cw=46178    ← 又重写,又长了
in=33036 cr=26968 cw=19360
in=35263 cr=0     cw=46349
```

三个独立签名:

- **cw 单调微增**:46115 → 46136 → 46178 → 46349 → 46370 → 46391 → 46562。
  每轮涨 20–200 token,正是新增一块 system 内容的体积。前缀在长个儿,自然永远命中不了。
- **同一前缀被反复重写**:cw > 10k 的 74 个请求中,79.7% 落在被重复 ≥3 次的千位桶
  (16k 桶 27 次、17k 桶 12 次、46k 桶 9 次)。健康的增量缓存 cw 应趋近 0,不该反复重写同一量级。
- **cr 在 0 与 46K 间交替**:706 个相邻对里切换 100 次。命中的轮次恰是"该轮没新增 system 块"的轮次。

08-18 更极端:`(cr+cw)/(in+cr)` 达 **250.3%**,缓存写入量是输入量的 2.5 倍——
同一份内容被反复写进缓存,这是"反复失效重建"最直白的度量。

### 5. 剂量-反应

把 `hub.log` 的提升块数 N 与 usage 记录按 ±6s 对齐(匹配 837 条):

| N(提升块数) | 请求数 | 命中率 | mean_in |
| --- | --- | --- | --- |
| 2–3 | 37 | 67.5% | 4,942 |
| 4–7 | 64 | 38.8% | 21,820 |
| 8–15 | 121 | 27.5% | 36,620 |
| 16–31 | 231 | 21.0% | 64,360 |
| 32+ | 378 | 11.8% | 138,801 |

单调递减,无一例外。

按天看的缓存覆盖率 `(cr+cw)/(in+cr)`:08-17 为 78.2%(提升率 0%),08-19 掉到 17.5%(提升率 100%)。
08-19 全天 86,665,644 输入 token 中,74,771,742(86.3%)按全价计费而非缓存读价。
若命中率恢复到 80%,这一天可少付约 5,744 万全价 token。

### 6. 一条重要的反面证据及其解释

08-18 提升率 95.4%,命中率却有 75.4%,单看这一天像是证伪。核对后不是反例:

- 那天 `mean_in` 只有 5,755(08-19 是 104,654),会话短,N 中位数 15(08-19 是 33);
  messages 本身体量小,前缀污染的绝对损失被掩盖。
- 而那天的覆盖率 250.3% 恰恰暴露了同一个病:内容被反复写入 2.5 倍。

即"同一个病的早期低剂量阶段",不是无病。

## 修复方向

按 AGENTS.md 的"默认放行"原则,首选方案就是**不动**:

1. **首选:对能接受 system-role 扩展的上游原样透传,不提升。**
   原样转发本身就是"能无损转 → 转",提升反而是有损重排。改动点是
   `prepare_request`(`claude1_protocol.py:2600-2608`)那个无条件分支,
   让它按上游能力(provider/compatibility 判定)决定是否调用 `_normalize_native_system_roles`。
   前置验证很便宜:发一个带 `messages[].role == "system"` 的探针请求给 direct 上游,
   看它是否 200。Claude Code 直连官方 API 时本来就这么发,官方是接受的;
   提升原是为 SGLang 一类严格实现准备的(见 `docs/anthropic-protocol-implementation-status.md:29`)。
   注意:现在提升后请求返回 200,只证明上游接受"提升后"的形状,
   **不构成上游会拒绝原始形状的证据**,所以这一步必须实测,不能推断。

2. **次选:必须提升时,落点不得进入缓存前缀头部。**
   把提升块留在原消息位置(例如转为 user 消息)而非搬到顶层 `system`,
   动态增量就仍在断点之后。代价是改动消息角色语义,需要单独权衡因果校验的边界。
   无论选哪条,硬约束是同一条:**逐轮增长的内容绝不能进 `system`。**

3. **观测补强:** 当前 warning 只记 `first` path 与计数,
   看不出提升块的体积,也看不出是否携带 `cache_control`。
   把这两项加进 `warning_details`,下次缓存回归就能直接从日志读出来,不必像这次一样反推。

4. **不改代码的临时规避:** 需要长会话缓存时绕过 hub 直连
   (`claude-provider-once.py:6976-6977` 的 `exec_plain_claude("direct")` 路径)。

按 AGENTS.md,改协议层需同步补测试;回归点是"同一会话连续两轮请求,顶层 `system` 逐字不变"。

## 已排除的可能

| 可能 | 排除依据 |
| --- | --- |
| 提升不幂等 / 拼接顺序不定 | 探针实测 `identical: True`,顺序由 `[*existing, *promoted]` 与 messages 索引确定 |
| `cache_control` 被丢弃或改写 | `copy.deepcopy` 整块搬运(`:2108`);native 路径不走 `_parse_request_ir`;全量日志无 `CACHE_CONTROL_DROPPED` |
| 断点被合并后指向不同文本 | 断点仍贴在原来那段 text 上,内容边界未变 |
| 5 分钟 TTL 过期 | 08-19 的 cache_creation 全部是 `ephemeral_1h`(3,120,962),`ephemeral_5m` 为 0;1h beta 透传正常 |
| 断点数量超上限被上游拒 | 请求均返回 200;且若那 N 条各带断点,N=52 时必然触发断点上限报错,故被提升的块本身不带 `cache_control` |
| count_tokens 双记污染统计 | 该渠道该模型无 `out == 0` 的行,`docs/review-findings-2026-08-17.md:90` 记录的双记缺陷未污染本次数据 |
| 并发 subagent 各自建缓存拉低均值 | 部分存在(08-19 有 57% 请求间隔 < 10s),但解释不了同一会话内 N 单调递增与 cw 反复重写同一量级前缀 |
| 1M context 门槛导致缓存策略变化 | 主体请求落在 100–200K,未越 200K 门槛;model 字段为 `claude-opus-5`,未带 `[1m]` |

## 置信度与最后一步

机制在代码层确定、在实况日志确认(x47→x52)、剂量-反应一致、三个后果签名互相独立且都吻合,
据此认定 system 提升为主因,置信度高。

需要诚实标注的残余混淆:剂量-反应表中 N 与会话长度高度共线,统计上无法完全分离二者。
不过正常情况下会话越长缓存命中率应越高,这里观测到严格相反的单调趋势,该混淆的方向与观测相悖。

一锤定音的验证(尚未做,因本次不改配置):同一 prompt 与同一会话历史,
分别经 hub 和绕过 hub 直连各跑若干轮,对比 `cache_read_input_tokens` 曲线。
若绕过 hub 后 cr 稳定在高位而 cw 趋近 0,则因果闭合。
