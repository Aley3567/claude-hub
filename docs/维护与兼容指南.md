# claude-hub 维护与兼容指南

桌面 `/Users/admin/Desktop/claude-hub` 是日常修改的主工作目录。这里同时包含
`claude1` 启动器和 `claude-hub` 网关，二者共用安装器、协议桥、测试和 Git
历史，不需要再去 Codex 的临时工作目录找源码。

## 最常改的地方

| 想调整的内容 | 文件 |
| --- | --- |
| 启动页、按键、列表、渠道选择体验 | `claude-provider-once.py` |
| 命名 Hub 目录校验、查找与路径解析 | `claude_hub_catalog.py` |
| Hub 路由、鉴权、转发、错误处理 | `claude-hub.py` |
| Anthropic / OpenAI Chat / OpenAI Responses 兼容 | `claude1_protocol.py` |
| shell 命令入口 | `zsh-functions.sh` |
| 安装和备份行为 | `install.sh` |
| Hub 无凭证配置模板 | `examples/claude-hub.example.json` |
| 界面原型和本机历史截图 | `docs/design-references/` |
| 回归测试 | `tests/` |

如果遇到“反人类”的交互，先在对应文件改小范围逻辑，再给 `tests/` 增加能复现
问题的用例。协议兼容问题优先放在 `claude1_protocol.py`，不要把不同上游的
特殊分支散落到启动器里。

命名 Hub 使用两层配置：`~/.cc-switch/claude-hubs.json` 是 v1 目录，`ready`
目录项引用独立的 Hub v2 配置；`setup` 目录项只引用 launcher 专用的首次设置
草稿。目录保存稳定 id、显示名、生命周期、顺序及相对路径；每份 v2 配置独立保存
端口、四槽、渠道、effort 和回退路由。旧目录项没有 `state` 时按 `ready` 读取，
所有 ready Hub 的端口必须互不冲突。

现有 `~/.cc-switch/claude-hub.json` 必须原地兼容：首次打开时自动登记为显示名
`Claude-Hub` 的目录项，只写目录引用，不移动也不改名旧文件。其目录条目为：

```json
{
  "version": 1,
  "default_hub": "claude-hub",
  "order": ["claude-hub"],
  "hubs": {
    "claude-hub": {
      "name": "Claude-Hub",
      "state": "ready",
      "config": "claude-hub.json",
      "log": "logs/claude-hub.log",
      "usage": "logs/claude-hub-usage.jsonl"
    }
  }
}
```

Hub v2 中，`default_channel` 是网关裸模型回退，`launch_slot` 是启动默认槽位，
二者不可合并。四个 `model_slots` 只能引用 `channels` 中已声明的模型，四个
`effort_by_slot` 由启动器写入本次会话临时 settings；不要重新加入全局
`effort_level` 或 `CLAUDE_CODE_EFFORT_LEVEL` 固定逻辑，否则会覆盖会话内原生
`/effort`。

启动首页是命名 Hub 选择面，只列 Hub，不显示模型或四个槽位。Enter 必须启动
当前 Hub 的 `launch_slot`；`m`、`→` 或 `Tab` 进入该 Hub 的 Slots / Channels
管理页。首页 `a`/`n` 创建空白 `setup` Hub，不得复制当前 Hub 的渠道、模型、
四槽或凭证；创建后立即进入四槽映射页。待配置 Hub 的 Enter、`m`、`→` 或
`Tab` 都只能恢复首次设置，禁止返回启动动作。四槽确认后才写完整 v2、分配端口并
切换为 `ready`；`r` 只改显示名，稳定 id、配置路径和运行身份保持不变。四槽
effort 调整和渠道增删都在当前 ready Hub 的管理页完成，不得跨 Hub 修改。

新增渠道向导固定为“渠道 → 模型 → 设置 → 确认”四阶段。模型阶段必须列出并默认
勾选 provider settings 中所有去重后的模型，支持空格多选，并保留手动添加模型 ID
的兜底。向导的数据接口只能新增渠道，禁止修改 `model_slots`；槽位绑定和替换仅能
从 Slots 管理页触发。阶段状态、模型家族、说明和选中行使用不同颜色层级。低于
10 行时压缩说明区，但仍应显示当前阶段、标题、至少一个选项和底部操作提示。

## 第一次在本机启用防泄漏门禁

```bash
cd /Users/admin/Desktop/claude-hub
./scripts/install-git-guards.sh
```

脚本只修改当前仓库的 `core.hooksPath`，会启用：

- `pre-commit`：扫描暂存区；
- `pre-push`：扫描即将进入远端的每个新提交，包括中间提交；
- GitHub Actions：在无本机私密数据的环境中扫描检出的仓库内容中的通用凭证模式和敏感路径。

本机扫描会只读加载环境变量、`~/.cc-switch/cc-switch.db` 和
`~/.cc-switch/claude-hub.json`，把真实凭证、渠道名、别名和上游地址作为
私密指纹。报告只显示类别、文件、行号和短哈希，不显示秘密值。

客户端 hook 可被 `git commit --no-verify` 跳过；GitHub Actions 也不能访问开发者
本机的私密指纹。因此，仓库内的检查不能保证拦住任意真实渠道名或上游地址。若要
强制该策略，需要在受保护分支要求 CI 成功，并由仓库管理员在服务端配置
`pre-receive`（或等效的受管密钥扫描）及其私密指纹来源。

手动检查命令：

```bash
python3 scripts/secret_guard.py --working-tree
python3 scripts/secret_guard.py --staged
python3 scripts/secret_guard.py --all-history
```

`--all-history` 用于人工审计；旧提交中的公开测试夹具可能被识别为通用秘密模式，
需要结合提交年代人工确认。日常自动门禁只检查当前内容和本次推送新增的提交，
不会因为远端早已存在的公开测试文本永久阻塞。

只有确认某一行是公开示例且属于误报时，才在该行加入
`secret-guard: allow <category>`。私密指纹还必须追加报告中的短哈希，例如
`secret-guard: allow private-provider-name 0123abcd45`；不要为真实凭证、真实
渠道或真实上游地址加豁免。

## 绝不进入仓库的内容

- `.env`、`.env.local` 等环境文件；
- `cc-switch.db`、`~/.cc-switch/` 的任何副本；
- `claude-hub.json`、`claude-hub-token`；
- API Key、OAuth Token、Bearer Token、私钥；
- 包含真实渠道名称、上游地址或备注的本机配置。
- `docs/design-references/local-private-*` 原始截图（可能把渠道名画进像素）。

示例配置只能使用明显的占位符。项目的 `.gitignore` 和 secret guard 会共同
拦截常见失误，但仍应在 `git diff --cached` 中人工确认提交范围。

## 修改后的固定验证顺序

```bash
cd /Users/admin/Desktop/claude-hub
python3 -m py_compile \
  claude-provider-once.py claude-hub.py claude_hub_catalog.py \
  claude1_protocol.py \
  scripts/secret_guard.py
python3 -m unittest discover -s tests -p "test_*.py" -v
./tests/test_shell_integration.zsh
./tests/test_install.zsh
python3 scripts/secret_guard.py --working-tree
git diff --check
```

需要把当前版本安装到本机时再执行：

```bash
./install.sh
source ~/.zshrc
claude1 doctor
```

`doctor` 是只读检查，不连接 provider。真实渠道联调应在上述离线测试全部通过
后进行，日志和错误信息中不得加入 token、完整上游 URL 或真实配置内容。

## 提交与同步

```bash
git status -sb
git diff --cached
git commit -m "简短说明"
git push
```

Git hook 会在提交和推送时自动检测，但 `--no-verify` 可跳过它们。不要使用该
选项；如果被拦截，按报告中的文件和行号删除敏感内容，再重新暂存和检查。受保护
分支上的 CI 与服务端策略才是不可由本地客户端绕过的门禁。
